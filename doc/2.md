# 项目文件树设计

## 1. 划分原则

项目按以下职责拆分，而不是按技术栈简单堆砌文件：

1. **公共接口**：定义统一请求、响应和后端协议，不依赖 vLLM 或自研引擎。
2. **后端适配**：分别实现 vLLM 和自研框架的 Adapter。
3. **自研引擎**：实现调度、KV cache、模型执行、采样和投机解码。
4. **模型与算子**：模型结构、TileLang 算子、C++/CUDA 实现分开存放。
5. **业务与服务**：Humanize 逻辑和 HTTP 服务不侵入推理引擎。
6. **测试与 Benchmark**：正确性测试、性能测试和测试数据可复现。
7. **源码与产物分离**：模型权重、编译产物和 benchmark 原始输出不提交 Git。

建议 Python 包名为 `evolution_infer`，采用 `src/` 布局。

## 3. 关键目录职责

### `api/`

公共接口必须保持轻量：

- 不导入 `vllm`；
- 不暴露自研引擎的 Scheduler、KV cache 或 CUDA Tensor；
- 不包含 Humanize 业务字段；
- vLLM 和自研后端共同遵守这里定义的输入输出语义。

建议将上一篇接口文档中的类型分别放入 `api/types.py` 和 `api/backend.py`。

### `backends/`

这里只做协议转换和生命周期管理：

- `vllm.py`：把 `SamplingParams` 转为 `vllm.SamplingParams`，把 vLLM 输出转为 `GenerateResponse`；
- `native.py`：调用自研 `Engine`，处理 tokenizer 和统一响应转换；
- `factory.py`：让 benchmark 和业务层通过配置选择后端。

不要把具体推理算法写到 Adapter 中。

### `engine/` 与 `modeling/`

两者职责不同：

- `engine/` 解决“请求如何执行”：调度、批处理、显存管理、采样和投机解码；
- `modeling/` 解决“模型如何计算”：Qwen 的网络结构和各层 forward。

后续替换模型时，主要扩展 `modeling/`，不应重写 Scheduler 和 KV cache。

### `kernels/` 与 `csrc/`

- `kernels/` 保存 Python 侧统一调用接口、TileLang DSL 和参考实现；
- `csrc/` 保存 C++、pybind11 和 CUDA 源码；
- `dispatch.py` 屏蔽不同算子实现，模型层不直接依赖某个 `.so` 文件；
- 每个高性能算子都应有对应参考实现及 `tests/kernels/` 测试。

编译生成的 `.so`、`.o` 和临时文件只能进入 `build/` 或构建工具指定目录，不散落在源码目录中。

### `humanize/` 与 `server/`

- `humanize/` 是可独立测试的 Python 业务层；
- `server/` 只负责 HTTP 协议转换，不实现检测循环或推理；
- Goal 1 阶段可以暂不创建 `server/`，避免提前引入无关工作。

### `benchmarks/`

benchmark 应直接并发调用统一的 `InferenceBackend.generate()`，由后端内部决定如何组 batch。

固定并记录：

- 模型权重、tokenizer 和 chat template；
- prompt 集合及输出长度；
- 解码参数和随机种子；
- warmup、并发度及请求速率；
- GPU、驱动、CUDA 和依赖版本。

原始输出与正式结论分开：原始输出放入被忽略的 `results/`，可复现方法和最终报告写入 `benchmarks/README.md` 或 `doc/`。

## 4. 依赖边界

推荐保持以下单向依赖：

```text
api
 ▲
 ├── backends/vllm ──→ vLLM
 ├── backends/native ──→ engine ──→ modeling ──→ kernels ──→ csrc/TileLang
 │
humanize
 ▲
server
```

benchmark 可以同时依赖 `api` 和 `backends/factory`，但不直接调用引擎内部模块。

需要避免：

- `api/` 导入 vLLM；
- `modeling/` 导入 HTTP 或 Humanize 代码；
- `humanize/` 直接操作 KV cache；
- 业务代码从 `tests/`、`scripts/` 或 `benchmarks/` 导入实现。

## 5. 分阶段创建，避免一次性铺满目录

### Goal 1：最小可运行链路

优先创建：

```text
src/evolution_infer/
├── api/
├── backends/
│   ├── vllm.py
│   └── native.py
├── engine/
└── modeling/qwen/

benchmarks/
tests/
configs/
```

先跑通“统一接口 → 两个后端 → 相同请求 → 统一响应”和基础 benchmark。

### 性能优化阶段

按需增加：

- `engine/kv_cache.py` 的高级管理；
- `engine/speculative.py`；
- `kernels/tilelang/`；
- `csrc/cuda/`；
- 对应算子和端到端正确性测试。

### 应用阶段

最后增加：

- `humanize/`；
- `server/`；
- 禁用句式规则包和交互式修改流程。

目录可以按阶段创建，不建议提前生成大量空文件。

## 6. Git 与文件存放规则

建议至少忽略：

```gitignore
build/
*.so
*.o
__pycache__/
.pytest_cache/
.venv/
models/*
!models/README.md
benchmarks/results/
```

其他约定：

- 模型结构代码放 `src/evolution_infer/modeling/`，模型权重放 `models/` 或 Hugging Face 缓存；
- 小规模固定测试输入可以提交，大型数据集只提交下载脚本和版本说明；
- 不在仓库根目录堆叠临时 `test_*.py`、`main.py` 和实验脚本；
- 原型验证完成后，将可复用实现迁回正式包，并补充测试；
- 当前 `doc/` 与 `docs/` 建议统一为 `doc/`，避免长期维护两个文档目录。
