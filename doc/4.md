# General 代码开发场景数据集规划

> 对齐文档：`doc/1.md`（统一 JSONL 格式与单调队列 DP 切分 $(i, l, r)$）、`doc/copy_locator.md`（Copy Locator 架构与在线无损验证）

## 1. 设计目标

`CopyGen` 数据集是为检验极端长片段精确复现而专门构造的试金石（绝大部分输出均为整段照抄）。为了证明 `Copy Locator`（及后续串联 `DSpark`）在真实软件工程场景下的通用加速价值，需要补充贴近工程师日常开发负载的数据集。

真实工程师使用 AI 辅助开发主要分两类交互形态，因此数据集按**双轨制**构建，并严格隔离评测集（Test）与训练源（Train）：

1. **Track A · 单轮一问一答**：控制变量，按「高 / 中 / 低」三档复制密度覆盖单文件编辑、带仓库上下文开发、从头写代码。
2. **Track B · 多轮 Agent 工作流**：还原工程师使用 Coding Agent（如 Claude Code、SWE-agent、OpenHands）在多轮工具调用、局部补丁修改与报错修复循环中的真实长上下文负载。

## 2. Track A：单轮一问一答数据集

保留并规范单轮代码评测的三档梯度（覆盖率参考值基于 `Qwen3.8-27B` 分词下长度 $\ge 16$ 的连续精确匹配统计）：

| 档位与定位 | 评测集（Test） | 推荐规模 | 数据来源与内容形态 | 输入可复制 / 含自重复 | 对应无泄漏训练源（Train） |
| :--- | :--- | :--- | :--- | :---: | :--- |
| **A1. 高复制**<br>IDE 单文件修改 | [`copilot-arena/editbench`](https://huggingface.co/datasets/copilot-arena/editbench)<br>*(备选：`nuprl/CanItEdit`)* | **108 条**<br>*(英文原题全集)* | CMU & UC Berkeley 从 458 位 VS Code 用户真实编辑记录中整理（ICLR / arXiv:2511.04486），采用整文件输出格式，自带单测 `test_code.py` | `~86.7%` / `~87.6%` | `Open-PerfectBlend` 的 `C2 + C3`（5.3 万条调试/重构）或 `InstructCoder`（GitHub commit 编辑三元组） |
| **A2. 中混合**<br>仓库上下文问答与开发 | [`lmarena-ai/repochat-arena-preference-4k`](https://huggingface.co/datasets/lmarena-ai/repochat-arena-preference-4k) | **80 ~ 100 条**<br>*(按仓库去重单轮代码子集)* | LMArena 真实用户将 GitHub 仓库多份源码塞入上下文（输入中位数 `~15.3K` tokens），要求补写单测、跨语言移植或按现有接口扩展功能 | `~13.3%` / `~17.2%` | 按仓库隔离后的其余 RepoChat 会话，或开源仓库构造的跨文件任务 |
| **A3. 低/零复制**<br>按需求从零写程序 | [`bigcode/bigcodearena-preference-5k`](https://huggingface.co/datasets/bigcode/bigcodearena-preference-5k) | **100 条**<br>*(单轮代码子集)* | BigCode 可运行编程竞技场真实用户请求，只给自然语言需求，从零编写算法、脚本或小型应用 | `~0.6%` / `~5.4%` | `Open-PerfectBlend` 的 `C7`（从头代码生成） |

- **`A1 (EDIT-Bench)`** 核心字段：`problem_id`、`instruction`、`original_code`（主要为 Python / TS / JS）、`highlighted_code`、`cursor_position`、`test_code`。既能测保留大量旧代码时的加速上限，又能直接跑单测汇报 `Pass@1`。
- **`A2 (RepoChat)`** 同一回答内既有可从输入复制的函数签名、配置与样板代码，也有大段新生成逻辑，适合检验 `Copy Locator <-> DSpark` 的动态切换。
- **`A3 (BigCodeArena)`** 作为**负向压力测试（Stress Test）**：验证几乎无原文可抄时，`Copy Locator` 能以极低开销判 `NO_COPY`（假阳性接近 `0%`），不会因误触发回滚拖慢纯生成速度。

## 3. Track B：多轮 Agent 开发工作流数据集

现代 Coding Agent 很少每次重默写整份文件，而是通过多轮工具循环完成开发。选用两套互补的公开轨迹数据集（会话总量均为万级，按仓库/会话 ID 切分后可同时提供固定评测集与训练源）：

| 子类与定位 | 数据集（Hugging Face） | 全量规模 | 评测抽样建议 | 数据来源与核心特点 |
| :--- | :--- | :--- | :--- | :--- |
| **B1. 真人日常 CLI Agent 会话** | [`nlile/misc-merged-claude-code-traces-v1`](https://huggingface.co/datasets/nlile/misc-merged-claude-code-traces-v1)<br>*(含上游 `archit11/claude-code-traces`)* | **32,000+ 会话** | 抽 **30 ~ 50 个**完整多轮工程会话（约 `300 ~ 500` 个生成轮次） | 真人工程师在日常项目中使用 **Claude Code** 的原始多轮记录，含真实系统提示词、`Grep / Read / Edit / MultiEdit / Write / Bash` 工具调用及人类追问修改 |
| **B2. 开源仓库排障多轮闭环** | [`thoughtworks/agentic-coding-trajectories`](https://huggingface.co/datasets/thoughtworks/agentic-coding-trajectories)<br>*(备选带沙盒验收：`SWE-bench/SWE-smith-trajectories`)* | **15,000 会话**<br>*(61.8 万轮，均长 ~41 轮)* | 按上下文长度桶（`4K / 16K / 32K+`）分层抽 **30 ~ 50 个**会话 | 专为 **LLM 推理引擎压测** 统一清洗的多轮语料，聚合 `SWE-agent`、`OpenHands` 等在真实 GitHub 仓库上读源码、`str_replace` 打补丁、跑 `pytest` 修报错的完整闭环 |

### 数据长相与典型结构

两套数据集的核心列均为序列化的多轮消息列表 `messages_json`（`thoughtworks` 额外提供 `agent_framework`、`n_turns`、`max_isl`、`total_tokens` 等统计列）。展开单条真实 Agent 会话的关键片段如下：

```json
[
  {"role": "user", "content": "Fix the race condition when cancelling tasks in src/worker.py and add a unit test."},
  {"role": "assistant", "content": [
    {"type": "thinking", "thinking": "Let's read src/worker.py first to inspect task cancellation..."},
    {"type": "tool_use", "name": "Read", "input": {"file_path": "src/worker.py"}}
  ]},
  {"role": "user", "content": [
    {"type": "tool_result", "content": "1: import asyncio\n2: class WorkerPool:\n...（数百行项目源码进入上下文）..."}
  ]},
  {"role": "assistant", "content": [
    {"type": "thinking", "thinking": "In `cancel_task`, `self._tasks.pop(task_id, None)` happens after `await task`..."},
    {"type": "tool_use", "name": "Edit", "input": {
      "file_path": "src/worker.py",
      "old_string": "  async def cancel_task(self, task_id: str) -> bool:\n    task = self._tasks.get(task_id)\n    ...（10~50 行原文件精确片段，必须 100% 逐字匹配上文 Read 输出）...",
      "new_string": "  async def cancel_task(self, task_id: str) -> bool:\n    task = self._tasks.pop(task_id, None)\n    ...（50%~85% 与刚生成的 old_string 或上文源码一致，仅改动核心几行）..."
    }}
  ]}
]
```

## 4. 覆盖的工作场景与加速机制矩阵

Track A 与 Track B 组合后，完整覆盖工程师日常开发的 **5 类典型场景**：

| 工作场景 | 主要数据来源 | 上下文与输出特征 | Copy Locator 核心作用与检验点 |
| :--- | :--- | :--- | :--- |
| **1. 搜索与阅读定位**<br>*(Explore / Grep / Read)* | `B1 / B2` 前序探索轮 | 上下文含目录树与搜索结果；输出为简短思考 + 读文件工具参数（`100 ~ 400` tokens） | 复制长文件路径与符号名；其余短推理步骤毫秒级判 `NO_COPY`，不引入额外开销 |
| **2. Agent 局部补丁编辑**<br>*(`Edit` / `str_replace`)* | `B1 / B2` 代码修改轮 | 上下文已含 `Read / view` 返回的完整源码；输出含 `old_string` + `new_string`（`300 ~ 1,500` tokens） | **Agent 核心高频收益区**：① `old_string` 必须 100% 原样抄自前文源码；② `new_string` 大段复用刚生成的 `old_string`（自身前缀复制）与原文件，仅改动行交由自回归 / `DSpark` |
| **3. IDE 整文件重构**<br>*(Whole-File Rewrite)* | `A1 (EDIT-Bench)` | 输入原文件（`1K ~ 4K` tokens）与修改指令，输出更新后的完整文件 | **单轮最高加速区**：`85%+` 未改动代码整段并行验证通过，配合单测验证无损输出 |
| **4. 报错排障与补写单测**<br>*(Test & Debug Loop)* | `B1 / B2` 中后程轮次、`A2 (RepoChat)` | 上下文累积至 `16K ~ 32K+`，同时含原文件、历史失败补丁与 `pytest` Traceback；输出修复补丁或新单测 | **长上下文消歧检验区**：上文存在多处高度相似的历史代码版本（长公共前缀重复），直接检验**逆向 RoPE 特征 $Y_l$** 的分叉消歧能力与长序列起点定位延迟 |
| **5. 从零编写新模块**<br>*(Greenfield Coding)* | `A3 (BigCodeArena)`、`B1 / B2` 新建文件轮 | 上下文仅含需求描述或少量接口定义，输出全新实现代码 | **稳健性检验区**：仅在输出内部出现重复分支/测试样板时触发自复制，其余位置稳定判 `NO_COPY` 零回滚损耗 |

## 5. 数据转换与评测接入规范

### 5.1 单步切面转换（直接复用 `doc/1.md` 格式）

无论是训练还是单步控制变量评测，都不需要新增数据格式：
- **单轮数据（`A1 / A2 / A3`）**：直接渲染为 `prompt_ids`。
- **多轮轨迹（`B1 / B2`）**：在轨迹中选定的第 $t$ 个 `assistant` 回复处切开，将此前全部消息 `messages[:t]`（含系统提示词、工具 schema、已读出的文件 `tool_result`、终端输出与历史对话）渲染为 `prompt_ids`。
- **生成与切分**：统一在目标底座 `Qwen3.8-27B` 上跑出该前缀下的真实 `cot_ids` 与 `output_ids`，直接复用 `doc/1.md` 的单调队列 DP（$k = 5,\, c = 4$）与三层选源优先级切出 `copy_cot`、`copy_output`，并额外记录元信息字段 `"turn_type"`（`explore` / `patch_edit` / `whole_file_edit` / `repo_qa_test` / `greenfield`）供分桶汇总。

### 5.2 两种评测模式

1. **单步前缀对齐评测（Turn-Level Replay）**：在完全相同的 `prompt_ids` 前缀上，对比 `AR`、`CopyGen`、`Copy Locator`（及后续 `Copy Locator + DSpark`）在开/关 CoT 下的输出一致性、草稿接受率、回滚率与纯解码吞吐（`tok/s`）。
2. **多轮整会话增量评测（Session-Level Replay，针对 `B1 / B2`）**：顺着会话轮次连续推进，跨轮保留底座 `KV Cache + 48 层 GDN` 状态，同时增量追加 `Copy Locator` 的正向特征 $X_j$、逆向 RoPE 前缀和 $F(j)$、区间词特征 $H_j$ 与 `StartIndex`，测量包含增量 Prefill 在内的整会话端到端耗时。

### 5.3 上下文上限与分桶汇报

- **放开上下文窗口**：`RepoChat` 输入中位数约 `15.3K` tokens，多轮 Agent 中后程常达 `16K ~ 32K+` tokens。评测脚本不再沿用早期 `smoke_vllm.py` 的 `10,240` 上限，统一将 `Cache(max_len=...)` 扩至 **`32768`**（超长会话桶扩至 `65536`），避免截断丢弃真实长样本。
- **分桶汇报指标**：最终报告不将不同性质的任务混成单一均分，固定按 **`EDIT-Bench` 整文件修改**、**Agent `Edit/str_replace` 补丁轮**、**Agent 排障/单测混合轮（含 `RepoChat`）**、**Agent 搜索定位短轮**、**`BigCodeArena` 从零生成** 五个子桶分别汇报加速比、草稿接受率、每千词回滚次数及 `EDIT-Bench` 单测通过率。
