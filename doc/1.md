# Goal 1：通用推理接口设计

## 1. 设计目标

为 vLLM 和自研推理框架定义统一的文本生成接口，使业务代码和 benchmark 不依赖具体后端。

本阶段只描述“一次文本生成”，不包含以下业务逻辑：

- 禁用句式检测及自动生成循环；
- 用户针对上一版结果提出修改意见；
- Humanize prompt 的构造；
- KV cache、CUDA Tensor、调度器等引擎内部状态。

这些功能应分别放在上层业务服务和后端内部实现中。

## 2. 总体结构

```text
HumanizeService / Benchmark
            │
            ▼
    InferenceBackend
       │          │
       ▼          ▼
 VLLMBackend   NativeBackend
                   │
                   ▼
 Tokenizer → Scheduler → ModelRunner → Detokenizer
```

- `VLLMBackend`：将统一请求转换为 vLLM 参数，并转换返回结果。
- `NativeBackend`：调用自研推理框架，内部实现调度、KV cache 和高性能算子。
- 上层只调用 `InferenceBackend.generate()`，替换后端时无需修改业务代码。

## 3. 核心接口

```python
from dataclasses import dataclass
from typing import Literal, Protocol


@dataclass(frozen=True, slots=True)
class SamplingParams:
    max_new_tokens: int = 256
    temperature: float = 0.0
    top_p: float = 1.0
    top_k: int = -1
    repetition_penalty: float = 1.0
    stop: tuple[str, ...] = ()
    seed: int | None = None


@dataclass(frozen=True, slots=True)
class GenerateHints:
    # 上一版输出的 token，仅作为投机解码提示。
    # 后端可以忽略该字段，且不能因此改变生成的语义。
    draft_token_ids: tuple[int, ...] | None = None


@dataclass(frozen=True, slots=True)
class GenerateRequest:
    request_id: str
    prompt: str  # 已完成 chat template 渲染的最终 prompt
    sampling: SamplingParams
    hints: GenerateHints | None = None


@dataclass(frozen=True, slots=True)
class GenerateResponse:
    request_id: str
    text: str
    output_token_ids: tuple[int, ...]  # 不包含 prompt token
    finish_reason: Literal["stop", "length"]
    prompt_tokens: int
    output_tokens: int


class InferenceBackend(Protocol):
    async def generate(
        self,
        request: GenerateRequest,
    ) -> GenerateResponse:
        ...
```

上层调用方式保持一致：

```python
response = await backend.generate(request)
print(response.text)
```

## 4. 接口约定

### 4.1 Prompt 由上层统一渲染

`GenerateRequest.prompt` 必须是已经套用过 chat template 的最终文本：

```text
用户输入
  → Humanize Prompt Builder
  → apply_chat_template
  → GenerateRequest.prompt
```

不能让 vLLM 和自研后端分别套模板，否则可能因模板、特殊 token 或 tokenizer 配置不同而产生不同的实际输入，使 benchmark 失去可比性。

模型路径、权重、dtype 和最大上下文长度等配置在构造后端时固定，不需要随每次请求传递。

### 4.2 保留输出 Token ID

`output_token_ids` 有两个用途：

1. 准确统计输出长度和吞吐；
2. 作为下一次生成的投机解码提示。

例如：

```python
next_request = GenerateRequest(
    request_id="request-2",
    prompt=rendered_prompt,
    sampling=sampling,
    hints=GenerateHints(
        draft_token_ids=previous_response.output_token_ids,
    ),
)
```

其中：

- 第一版 `VLLMBackend` 可以忽略 `hints`；
- `NativeBackend` 后续可以使用这些 token 构造 draft，再交给目标模型并行验证；
- 如果上一版输出属于模型上下文，它仍必须完整包含在 `prompt` 中，不能只放在 `hints` 中；
- `hints` 只是性能提示，后端不支持时可以忽略，不得影响请求语义；
- KV cache 指针、CUDA Tensor 和调度器状态不得暴露到通用接口中。

### 4.3 使用异步单请求接口

暂时不定义 `generate_batch(texts)`。批处理应由引擎内部完成：

- benchmark 并发提交多个 `generate()`；
- vLLM 和自研 Scheduler 各自组织 batch；
- 更接近真实服务，也便于后续实现 continuous batching。

### 4.4 性能指标与生成结果分离

统一响应只包含生成结果及 token 数量，不强制包含延迟等内部指标。

- 端到端延迟、P50/P95 和吞吐由 benchmark 在外部测量；
- prefill/decode 时间、draft 接受率等引擎指标单独记录；
- 不要求 vLLM 与自研框架提供完全一致的内部指标。

## 5. Humanize 业务接口

Humanize 功能应在推理接口之上单独设计，例如：

```python
@dataclass(frozen=True, slots=True)
class HumanizeRequest:
    text: str
    rule_pack: str = "default"
    instruction: str | None = None       # 用户对上一版的修改意见
    previous_output: str | None = None   # 上一版结果
    max_rounds: int = 3
    sampling: SamplingParams = SamplingParams()
```

`HumanizeService` 负责：

1. 构造并渲染 prompt；
2. 调用 `InferenceBackend.generate()`；
3. 检测禁用句式；
4. 决定继续生成还是返回结果；
5. 将上一版输出的 token ID 作为下一次生成的 `GenerateHints`。

这样可以独立替换推理后端，而不修改 Humanize 业务逻辑。

## 6. 后续扩展

流式输出应使用独立方法，例如：

```python
def generate_stream(...) -> AsyncIterator[GenerateChunk]:
    ...
```

不要通过 `stream=True` 让 `generate()` 返回不同类型。流式接口可在核心非流式链路稳定后再实现。

如果后续需要 HTTP 服务，可以在统一 Python 接口之外增加 FastAPI，或适配 OpenAI `/v1/chat/completions`。Goal 1 不需要先绑定具体 HTTP 协议。

## 7. 推荐实施顺序

1. 实现最小统一接口及 vLLM、自研框架两个 Adapter。
2. 固定模型、prompt 和解码参数，验证两条链路的结果一致。
3. 基于统一接口完成端到端延迟和吞吐 benchmark。
4. 为 `NativeBackend` 增加基于 `draft_token_ids` 的投机解码优化。
5. 最后增加流式输出及 Humanize 业务接口。
