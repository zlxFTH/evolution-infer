### 1. 【最关键 · 训练标签 Bug + 冷启动瓶颈】`MAX_CANDIDATES=32` 截断导致 `96.8%` 的起点正样本被错标成了 `NO_COPY`

看服务器上的两处代码联动：
- `src/copy_locator/candidates.py:29`：
  ```python
  ranked = nlargest(MAX_CANDIDATES, ((self.suffixes.get(pos, 0), pos) for pos in positions[:count]))
  ```
  在每段复制的第 0 步（冷启动，`overlap` 大多同为 `0` 或 `1`），元组 `(overlap, pos)` 平局时只按 `pos` 取最大的 32 个——也就是**只保留了 prompt 最末尾的 32 次出现，把代码文件前 70% 里的真实起点全扔掉了**（所以 836 个区间开头只有 27 个进池）。
- **更隐蔽的连锁 Bug 在 `train/train_copy_locator.py:63-69`**：
  ```python
  target = 0
  if left >= 0:
    ... # 在 candidates 前 32 个里找匹配，找不到时 target 保持为 0！
  ```
  训练代码虽然特意加了 `early_sample` 采样冷启动位置（`d < 5`），但因为前 32 个候选里没有真实起点，`target` 落回了默认值 `0`（即 `NO_COPY`）！**相当于亲手把 809/836 个冷启动正样本标成 `NO_COPY` 喂给模型学**，逼着模型在每段开头第 0 步不敢触发，白白多走 1 步慢速单词解码（每段白丢 `~51 ms`）。

**优化做法**：
1. 把 `MAX_CANDIDATES` 从 `32` 提到 `128` 或 `256`（2000 词上下文里同 token 出现一般不超过 200 次，`[256, 1025]` 过一次 `GatedMLP` 仅需 `~0.02 ms`，换回省掉的 1 步 27B 解码 `51 ms` 血赚）；
2. 训练时若某个正样本（`left >= 0`）仍未落入候选池，该锚点的 `start_loss` 设为 `ignore_index=-100` 跳过，**绝不能标成 `0`（`NO_COPY`）**；
3. 开启 CoT 后同一片段可能在 `prompt` 和 `cot` 中各出现一次（都是合法无损源），建议将 `start_supervision` 里的 `break` 单标签改为多正例对数似然 $-\log \sum_{i \in \text{valid}} p_i$，避免两个完全等价的真起点互相压梯度。

### 2. 【立竿见影拉开差距】对 CopyLocator 放开 `max_copy_len=128` 的人为限长

看 `checkpoints/copy-locator-candidates-20261126-234426/results.jsonl` 的真实明细：
- 第 3 题要抄 `865` 个词，CopyLocator 接受率 **865/865（100%）**，但因为评测传了 `--max-copy-len 128`，硬生生被切成了 **10 次独立验证**（第 2、8 题 640+ 词也被切成了 7~8 次）。
- **CopyGen 必须限长 128**（因为它的 `log_length` 是瞎猜的，放开就会猜过头触发昂贵的回滚重放）；但 **CopyLocator 本就是看着边界定精确终点 $r$**（7/8 题零越界）。
- 每次人为截断都会多做一次 `cache.snapshot()`（克隆 151 MB GDN 状态）+ 多跑一轮 64 层小步长前向。把 CopyLocator 的 `max_copy_len` 放开到 `512` 或不限长（`None`），长段一次前向直接抄完，纯解码吞吐会进一步大幅甩开 CopyGen。

### 3. 【最大硬件瓶颈】`src/qwen.py` 里 48 层 GDN 的 Python 串行循环吃掉了大部分加速比

从 `results.jsonl` 拆出第 3 题的耗时账：
- 单步 AR 解码 1 个词耗时 **`51 ms`**；
- 但单次并行验证 ~86 个词居然耗时 **`320 ms`**，Prefill 2100 词耗时 **`6.79s`**（这直接导致含 prefill 吞吐从 `135.5` 被拖低到 `61.6 tok/s`）。
- 原因在 `src/qwen.py:191`：`LinearAttention.forward` 里的 `for t in range(seq_len):` 在多 token 验证时从 Python 串行发射了数万个碎算子。
- **优化做法**：哪怕不接第三方库，只把这段 GDN 递推函数单独包一层 `@torch.compile`（或改用 chunked GDN / `flash-linear-attention`），多 token 并行验证会从 `320 ms` 压回 `~45~60 ms`，CopyLocator 的解码吞吐能直接冲上 `250~300+ tok/s`。

### 4. 【特征增强】起点打分 `mlp_start` 补入前驱特征 `x[pos - 1]` 对齐因果相位

- 目前 `src/copy_locator/model.py:66-72` 输入的是 `[q, x[pos], log1p(overlap)]`：
  - `q = x[visible - 1]` 处于“刚读完前一个词、准备预测 `next_id`”的相位；
  - 而 `x[pos]` 处于“已经读进 `next_id`、正在预测**下下个词**”的相位。
- 改为拼接 **`[q, x[pos - 1], x[pos], log1p(overlap)]`**（`pos == 0` 时前驱填零或哨兵）：`q` 与 `x[pos - 1]` 同相位比对上文语境，同时 `x[pos]` 提前校验第 2 个词的走向，冷启动（`overlap=0`）时的语义消歧能力会明显更强。

### 5. 【低成本工程清理】两处 CPU / 显存开销可顺手消掉

1. **`src/cache.py:41-46` 的 `snapshot()` 避免反复 `clone()` 分配显存**：每次验证前都新建 96 个张量（约 151 MB），可以在 `Cache.__init__` 里预留一份静态快照 buffer，`snapshot()` 时只做原地 `.copy_()`。
2. **`src/copy_locator/candidates.py:17-25` 的 `StartIndex.extend()`**：
   - 第 24 行 `self.suffixes[self.visible] = self.visible - self.prompt_len` 沿着主对角线 `pos == visible` 走，永远大于 `visible - min_copy`，属于无效死计算，可以直接删掉；
   - 目前每提交 1 个词都全量重建 `self.suffixes` 字典，在拷贝大段或跑上万词长 CoT 时会有不必要的 Python 循环开销；其实只需维护 `self.history` 和 `positions` 列表，仅在调用 `candidates(next_id)` 时对候选位置往左比对几个词算 `overlap` 即可（拷贝几百词期间中间位置根本不需要算后缀字典）。
